# LAN Drop 面试设计说明

## 1. 项目定位

LAN Drop 是一个“单主机 + 多客户端”的局域网文件中转站：一台电脑运行 Go 服务，同一网络中的电脑可用浏览器连接，三星手机也可用原生 Android 客户端拍照或选文件上传。

这个定位与纯 P2P 工具不同：文件落在主机共享目录中，所有已授权设备看到同一份权威文件列表。这使得系统很适合临时会议室、宿舍、家庭网络和无外网环境。

## 2. 开源项目对标

| 项目 | 它解决得好的问题 | LAN Drop 借鉴 | 暂不照搬的原因 |
| --- | --- | --- | --- |
| [LocalSend](https://github.com/localsend/localsend) / [Protocol](https://github.com/localsend/protocol) | 多端发现、HTTPS 指纹、预传输握手、并行文件上传和 SHA-256 校验 | SHA-256 与完整性元数据；后续增加 mDNS/组播发现和可选 TLS | 自签证书在纯浏览器中有信任体验问题，会增加上手成本 |
| [croc](https://github.com/schollz/croc) | 中继、PAKE 端到端加密、中断恢复和跨网络传输 | 把“可恢复的分片上传”作为下一个核心能力 | 公网中继会改变项目的信任和运维模型 |
| [PairDrop](https://github.com/schlagmichdoch/PairDrop) | WebRTC 点对点传输、WebSocket 信令、公共房间、设备配对和进度体验 | 多浏览器实时更新；当前用 SSE 以更小复杂度实现 | WebRTC 需要 STUN/TURN 与信令服务，对“文件落在主机”的产品定位收益不大 |
| [File Browser](https://github.com/filebrowser/filebrowser) | 成熟的 Web 文件管理、用户体系和反向代理部署 | 健康检查、请求追踪、登录防爆破和明确的部署边界 | 多用户权限、在线编辑和命令执行会显著扩大攻击面 |

对标不是为了堆功能，而是为了选择与定位一致的复杂度。LAN Drop 当前优先做 HTTP 传输路径的可靠性，而不是提前引入公网中继。

[File Browser 的官方安全公告](https://github.com/filebrowser/filebrowser/security/advisories/GHSA-cm2r-rg7r-p7gg)也说明：有登录页并不代表认证链路已经完整，密码策略和防暴力尝试需要单独设计。这是 LAN Drop 本轮加入每 IP 登录限流的直接理由。

## 3. 已落地的面试亮点

### 大文件流式传输

`io.Copy(io.MultiWriter(temp, hash), source)` 让文件边写磁盘边计算 SHA-256，内存占用不随文件大小线性增长。`io.LimitReader` 和 `http.MaxBytesReader` 在两层限制请求大小，避免超大请求持续消耗磁盘。

可讲的取舍：SHA-256 会增加 CPU 成本，但它与磁盘写入同步完成，不需要再次读取整个文件。

### 原子发布与一致性

上传首先写入隐藏临时文件，成功后才 `Rename` 到最终文件名，客户端不会看到半个文件。元数据索引也采用“临时文件 + `Sync` + `Rename`”，避免进程中断留下半截 JSON。

可讲的取舍：文件和索引不是一个真正的跨文件事务，所以服务启动时会扫描共享目录并重建权威状态。

### 并发控制

`sync.RWMutex` 保护内存索引和同名文件分配：列表读取可并行，命名、发布和索引更新在同一个写锁临界区内。24 个 goroutine 并发上传同名文件的测试会验证最终文件名唯一，整个测试集在 race detector 下运行。

可讲的取舍：文件内容的流式写入在锁外，避免大文件阻塞其他上传；只把短暂的发布阶段放在写锁内。

### SSE 实时同步与背压

浏览器通过 `/api/events` 建立 Server-Sent Events 长连接。上传或删除后，事件广播给所有已授权客户端，客户端再拉取权威列表。每个订阅者使用有限缓冲 channel，发布是非阻塞的；慢客户端可以丢失中间通知，但不会阻塞所有上传。

这个设计成立的前提是：事件只是“状态失效信号”，而不是必须全部消费的业务日志。真实状态始终来自 `/api/files`。

### 认证与威胁边界

- 连接码用常量时间比较，成功后写入 `HttpOnly` + `SameSite=Strict` Cookie。
- 每个客户端 IP 在一分钟内连续失败 5 次会被暂时阻止，返回 `429` 和 `Retry-After`。
- 限流器故意不信任 `X-Forwarded-For`，因为默认部署没有可信反向代理，这个 Header 可被客户端伪造。
- 文件名会规范化，下载和删除拒绝包含路径分隔符的名称。

必须主动说明：默认 HTTP 只适用于可信局域网，连接码不等于传输加密。公共网络中应使用 TLS 反向代理或 VPN。

### 可观测性与工程化

- `/healthz` 返回健康状态和运行时长，便于容器、systemd 或反向代理做存活检查。
- API 请求返回 `X-Request-ID`，并记录方法、安全路径、状态码、响应字节和耗时。
- GitHub Actions 分别执行 Go 依赖校验、`go vet`、race test、服务端构建，以及 Android 单元测试、lint、APK 和 instrumentation test APK 编译。

### 三星 Android 客户端与最小权限

- 原生客户端使用 Kotlin、Jetpack Compose、`ViewModel + StateFlow`，界面只消费不可变状态，网络任务绑定生命周期。
- 拍照交给三星系统相机的 `TakePicture` 合约，应用不申请 `CAMERA`；非导出的 `FileProvider` 只向相机临时授权一个缓存 URI。
- 用户拍摄后先看到预览，可重拍、取消或确认上传。服务器地址可保留，连接码只存在当前进程内，不以明文写入偏好设置。
- 文件用 64 KiB 缓冲流式上传；取消任务时重新抛出 `CancellationException`，避免“用户取消”被错误展示为“上传失败”。
- Android 17 才按需申请 `ACCESS_LOCAL_NETWORK`，旧版本不弹无意义权限；HTTP 只允许私网地址，公网端点必须使用 HTTPS。
- 客户端禁用 API 自动重定向，避免私网服务器用 3xx 把自定义认证 Header 带到另一个主机。

可讲的取舍：CameraX 能提供自定义取景器，但会扩大相机权限、设备兼容和生命周期处理范围。当前产品只需要“拍一张并上传”，复用系统相机的可靠性和用户熟悉度更有价值。

## 4. 实测数据

基准命令：

```bash
go test ./internal/storage -run '^$' -bench BenchmarkStoreSaveAndDelete1MiB -benchmem -count=3
```

在 Apple M5 本机上，1 MiB 数据的“写入 + SHA-256 + chmod + 原子索引 + 删除”整体吞吐约为 98–102 MB/s，约 39 KB/op、75 allocs/op。

这个数据不是网络峰值，也不能代表所有磁盘。它的作用是提供可重复的性能基线，后续做分片、缓冲或索引优化时可以用数据验证。

`go test ./... -cover` 的当前结果为：`internal/server` 82.2%，`internal/storage` 78.4%。`cmd/lan-drop` 包含操作系统地址发现和打开浏览器的适配代码，当前覆盖率为 15.4%；因此展示时分包说明，不用一个总数掩盖差异。

## 5. 演进路线

### P1：已完成

- SSE 实时文件列表同步，包含心跳、断开清理和慢客户端背压策略。
- 登录防爆破、`Retry-After` 和可清理的有界内存状态。
- 请求追踪、健康检查、并发测试、性能基准与 CI。
- 三星 Android 原生客户端、拍照预览上传、最小权限与 Android 17 局域网适配。

### P2：可恢复分片上传

上传会话协议可以设计为：

1. `POST /api/uploads` 提交文件名、大小和预期 SHA-256，创建 upload ID。
2. `HEAD /api/uploads/{id}` 返回服务端已确认 offset。
3. `PATCH /api/uploads/{id}` 从该 offset 追加分片，不匹配时返回冲突而不是重复写入。
4. 完成时校验大小与摘要，再原子发布为正式文件。

核心问题不是“怎么切块”，而是 offset 幂等、进程重启后恢复、过期会话清理、并发分片冲突和最终摘要验证。

### P3：自动发现与可选加密

- 通过 mDNS 或组播广播服务名、端口和协议版本，同时保留二维码作为 AP 隔离等环境下的回退。
- 提供可选 TLS，并在配对界面展示证书指纹；不把“忽略证书警告”作为默认操作。

## 6. 90 秒面试讲法

> 我做的是一个 Go 局域网文件中转站，主机运行单二进制，电脑可直接用网页，三星手机还有原生拍照上传客户端。大文件不会整体进内存，而是流式写入临时文件、同步计算 SHA-256，再原子发布；我用 RWMutex 保护命名和元数据一致性，并用 race test 验证并发。多客户端通过 SSE 同步，事件只是状态失效信号，所以慢客户端不会反压上传。Android 端复用系统相机和 FileProvider，不申请相机或媒体权限，连接码也不落盘。安全上还有常量时间认证、登录限流、路径穿越防护，并明确把默认 HTTP 限定在可信局域网。

如果面试官继续深挖，优先展开“为什么 SSE 事件可丢失”、“如何保证同名并发上传的唯一性”、“原子 Rename 的边界”和“分片上传如何实现幂等恢复”。
